Privacy Policy

2. Information the bot processes

What is processed depends on which features a server enables and how members use them. This list is based on the bot's source code.

  • Discord identifiers: user, server, channel, role and message IDs, plus usernames, display names and avatar references, used to run commands and to record settings, logs and tickets.
  • Server configuration: the command prefix; channel and role IDs; ticket, verification and voice settings; and the AutoMod, Anti-Nuke and AntiBot settings. These are stored in Firestore.
  • Message content, in memory: AutoMod, the bad-word filter and link checks read message text in order to decide whether a message breaks a rule.
  • Message content, copied to Discord: when the bad-word filter removes a message, up to 1,000 characters of it, with the author's ID and channel, can be posted to the server's moderation-log channel. That copy stays in Discord and is not stored in Firestore by that code path.
  • Deleted messages, in memory: the snipe feature keeps up to 15 deleted messages per channel in the bot's memory so staff can view them. Nothing is written to Firestore for this.
  • Quoted messages, in memory: the quote feature keeps up to 400 characters of the message being quoted, and the requester's ID, for up to one hour. The generated quote image is sent to Discord and is not removed when that memory expires.
  • ModMail: direct messages sent to the bot before a ticket is opened are stored in Firestore (modmail_pending), including message text and attachment links, until they are forwarded to a ticket or dropped. Ticket records (modmail_tickets) store IDs, status and timestamps. Ticket conversations happen in Discord channels.
  • Moderation records: warnings (reason, moderator tag, timestamp), strikes and strike counters, and case records (target and moderator names, and a reason of up to 2,000 characters). These are stored in Firestore.
  • Staff activity: Active Time counters for online time, voice time, staff messages and selected moderation commands, plus daily and historical totals, all stored in Firestore by server and user ID.
  • AFK: the AFK reason and timestamps, stored in Firestore and in memory.
  • Verification: captcha answers are held in memory for up to 60 seconds. Verification review records (decisions and notes) are stored in Firestore.
  • Temporary voice rooms: the room's channel ID, owner ID, server ID and creation time, stored in Firestore while the room exists.
  • Anti-Nuke: when a member is quarantined, their previous roles are stored in Firestore (quarantine_role_snapshots) and removed when they are released. The undo buffer for deleted channels and roles is held in memory for up to two minutes, up to 200 entries, and includes channel and role names and permission overwrites.
  • Access lists: IDs of delegated server owners, servers approved by the bot owner, and users granted no-prefix access, with who granted each entry and when.
  • Operational data: runtime logs. If the operator sets a console-mirror channel, some log lines, which may include names, IDs and error details, are posted to that Discord channel. When Firestore quota is exhausted, writes can wait in the bot's memory for up to 50,000 operations or 48 MB.

3. The web dashboard

Discord sign-in (OAuth2). You sign in through Discord, and the dashboard requests two scopes: identify and guilds. The dashboard receives your user ID, username, display name and avatar reference, and the list of servers you are in, with each server's ID, name, icon, owner flag and permission bits. The dashboard keeps this list in your session. It does not store your Discord access token; the token is used only during sign-in. The dashboard keeps a hashed form of the token in memory only for rate-limit bookkeeping.

Live permission checks. Each protected request checks your current server membership, owner status and permissions with Discord, using the bot. Access comes from that live check, not from the sign-in snapshot alone. Delegated owners must also be on the server's owner list.

Cookies and sessions. The dashboard sets one first-party cookie, friday.sid. It is HTTP-only, uses SameSite=Lax, and is marked Secure in production. It lasts up to eight hours. The cookie identifies a session; the session data itself is held in the dashboard server's memory, not in Firestore. Sessions are capped at 500 and are cleared when the service restarts or redeploys, so you may need to sign in again. Signing out destroys the session. The dashboard uses no advertising or third-party cookies.

Browser storage. The dashboard stores some interface preferences in your browser's localStorage: directory filters, favourite servers and setup-guide progress. These contain no tokens.

Records stored from dashboard use:

  • Configuration and protection settings (guild_configs, protection_configs, antibot_configs, command_permissions, server_owner_access), including trusted-user lists.
  • Dashboard audit events (dashboard_audit_logs): the acting user's ID and display name, the action, the names of changed settings, and a target user ID where relevant. Up to 75 events are kept per server.
  • Configuration snapshots (dashboard_config_versions): the saved configuration and protection settings, the actor, a reason of up to 120 characters, and a timestamp. The latest 30 snapshots are kept per server.
  • Appeals (punishment_appeals): the user ID, case ID, action, reason, status and timestamps.
  • ModMail threads and DM sessions (modmail_threads, modmail_dm_sessions): staff can list up to 100 threads per server. A DM session record links a user to a thread and is removed when the thread is closed. [ACTION REQUIRED: confirm whether thread records store message text, and for how long.]
  • Case notes and cases (friday_cases, friday_case_notes), verification reviews (friday_verification_reviews), and published messages (friday_studio_messages): these hold the note or review text, the content and embeds of published messages, channel details, and the creator's user ID.
  • Emergency lockdowns (emergency_lockdowns): channel permission overwrites are saved while a lockdown is active so they can be restored. [ACTION REQUIRED: confirm whether these snapshots are deleted after restore.]

Dashboard pages also keep a staff display-name cache in the server's memory for up to 24 hours. It is not written to Firestore.

4. Why information is processed

Information is used to run the commands and features a server enables; to route and answer ModMail and support tickets; to record and review moderation actions and appeals; to apply AutoMod, Anti-Nuke, AntiBot and verification rules; to manage temporary voice rooms; to produce staff activity reports; to check access to dashboard pages; to publish messages you choose to send through the dashboard; to prevent abuse; and to diagnose and fix failures.

5. Where information is stored

  • Firestore (Google Cloud): the persistent records described in sections 2 and 3.
  • Server memory on hosting (Render): dashboard sessions, rate-limit counters, snipe and quote memory, the Anti-Nuke undo buffer, captcha state and the Firestore write queue. These are lost when the service restarts or redeploys.
  • Discord: messages, ticket channels, transcripts, moderation-log posts, role and permission changes, and audit-log entries. Discord keeps these under its own policies, and deleting a copy in FRIDAY does not delete it from Discord.
  • Hosting logs: Render keeps service logs under its own settings. [ACTION REQUIRED: confirm log retention on the hosting account.]
  • GitHub Pages: this legal site is static and stores no user data.

6. Retention and deletion

There is no single retention period. The list below shows what the code does today. Where the code has no automatic deletion, this policy says so.

  • Deleted automatically: AFK records are removed when the member next speaks in that server. Voice-room records are removed when the room's channel is deleted. Quarantine role snapshots are removed when the member is released. Dashboard sessions expire after eight hours and are cleared on restart. Captcha state expires after 60 seconds, quote memory after one hour, and the snipe and Anti-Nuke undo memory is cleared on restart or after its limit.
  • Capped, not time-limited: dashboard audit events (75 per server) and configuration snapshots (30 per server) are kept until they are pushed out by newer entries.
  • Reset, not deleted: the daily staff-activity reset sets totals to zero. The records and any historical snapshots remain.
  • Kept until removed: pending ModMail messages remain until forwarded or dropped. If a member starts a DM and never completes server selection, that message can remain in Firestore; no automatic expiry was found. Closed ticket records, warnings, strikes, case records, case notes, appeals, verification reviews, ModMail threads and published-message records have no automatic expiry in the code.
  • Discord copies: ticket transcripts, moderation-log posts and quote images stay in Discord after the source record is removed, until someone deletes them there.
  • After the bot leaves a server: Firestore configuration, access lists and records are not automatically erased.

7. How data is shared

FRIDAY does not sell personal information. Information is shared with the following providers, each of which processes it under its own terms:

  • Discord: sign-in, messages, channels, roles, audit logs and logs posted to Discord.
  • Google Cloud (Firestore): persistent records.
  • Render: hosting for the bot and dashboard, server memory and service logs.
  • GitHub: hosting for this legal site and for the source code.
  • YouTube and Wikipedia: when those optional features are used, the search term or channel URL is sent to them.

Information is visible to server owners and staff who have access to the relevant channels or dashboard controls. It may be disclosed where the law requires it, or where needed to address security, abuse or harm. 8. Server administrators and their controls

Server administrators can turn features on or off, choose which channels and roles the bot uses, restrict channel permissions, review and change dashboard settings, and remove the bot. Several commands remove specific records. These controls do not delete copies in Discord, at Firestore, or in provider logs. Administrators are responsible for the channels they set up and for the members' information those channels contain.

10. Security

The dashboard sends security headers that restrict scripts and framing. Its session cookie is HTTP-only and Secure in production. State-changing requests must come from the dashboard's own origin. Sign-in uses an OAuth state value. Protected actions check Discord permissions live. Rate limits apply to sign-in and to API calls. The bot and dashboard read their secrets from environment variables rather than source code, and the dashboard refuses to start in production without a session secret. Those are the measures the code shows.

No system is completely secure. [ACTION REQUIRED: the Firestore security rules, IAM settings and backup arrangements were not reviewed here and are not described.]

11. Children and age

F.R.I.D.A.Y is intended for users who are old enough to use Discord under Discord's own rules. 12. Legal framework and its timing

The DPDP Act, 2023 and the Digital Personal Data Protection Rules, 2025 were notified in November 2025 and are being brought into force in stages. The Data Protection Board was established in November 2025. Consent-manager provisions start in November 2026. The main obligations, including notice, consent, security safeguards, breach notification, data principal rights and children's data, are scheduled for May 2027. Official gazette dates for these stages differ by a day across sources. [ACTION REQUIRED: counsel to confirm the exact commencement dates from the gazette.]

Section 43A of the Information Technology Act, 2000 and the SPDI Rules are scheduled to be omitted with the main obligations. Sources disagree on whether they already stopped applying. [ACTION REQUIRED: counsel to confirm which regime applies on the publication date.]
