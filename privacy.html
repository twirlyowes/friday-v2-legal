Privacy Policy

Effective date: 17 October 2026
Service: F.R.I.D.A.Y Discord application (“F.R.I.D.A.Y”, “the Bot”, or “the Service”)
Project: F.R.I.D.A.Y on GitHub

Scope: This policy is based on the publicly accessible main branch of the repository reviewed on 17 October 2026. The code deployed on the live bot, provider settings, and server-specific configuration can differ. The maintainers should keep this policy aligned with the actual deployment.

1. Information processed

Depending on server configuration and the features used, the Bot processes the following information:

  • Discord account and server identifiers: Discord user, server, channel, and role IDs; usernames/tags and avatar references where shown in tickets, moderation output, logs, or quote images.
  • Server configuration: prefixes, selected channel and role IDs, ticket category and log-channel settings, verification roles/channels, voice-room settings, bad-word lists, YouTube notification configuration, and optional server reply text (such as a configured IP message). These settings are stored in Firestore.
  • ModMail messages and attachments: DMs sent to the Bot, message text, attachment URLs, file names, content types, and timestamps may be written to the modmail_pending Firestore collection while a ticket is awaiting setup. Once a ticket is open, messages and attachments are relayed to the Discord ticket channel and between the ticket channel and the member's DMs. Ticket metadata includes the member ID, server/channel IDs, category, status, timestamps, and IDs of staff who claim or close it.
  • Ticket transcripts: when a ticket is closed and the server has a configured ticket-log channel, the Bot attempts to create a text transcript containing message timestamps, authors and IDs, message text, attachment names/URLs, ticket metadata, and the staff member who closed the ticket. The transcript is uploaded to that Discord channel if the upload succeeds.
  • Moderation information: warning and strike records can include the target's ID, server ID, reason, timestamp, and moderator identifier or tag. Reasons and action details may also appear in Discord messages, server-configured log channels, and Discord's own audit log.
  • Content examined for moderation: the Bot processes guild message content to parse commands and run configured bad-word/link filtering. When the filter removes a message, the message text (up to 1,000 characters in the log description), author ID, and channel information may be posted to the configured moderation log channel. Edited-in links can also be logged.
  • Staff activity: for members in the configured activity/staff role, the Bot counts active/online time, voice time, message count, and selected moderation-command counts. These numeric totals, a guild/user key, and an update timestamp are saved in Firestore and may appear in reports sent to Discord channels.
  • AFK information: an AFK reason and timestamps, along with limited nickname-restoration state, are stored by server and user ID until the AFK record is cleared.
  • Recently deleted messages: the snipe feature keeps up to 15 deleted messages per channel in process memory, including message text, author reference, time, and an attachment image URL where available. This cache is not written to Firestore; it is limited by the 15-entry cap and is cleared when the running process restarts.
  • Temporary voice-room records: Firestore records may include a temporary channel ID, owner user ID, server ID, and creation timestamp.
  • Verification session data: captcha answers, attempts, and short-lived cooldown/session state are held in process memory while verification is in progress; the reviewed code sets a 60-second timeout for a pending captcha. Verification also changes Discord roles as configured.
  • Quote-image data: when a member runs the quote command, the Bot temporarily holds the quoted text (up to 400 characters), source author's display name/username and avatar image, and requester's ID in memory. The editable quote state expires after about one hour or when removed. The resulting image is a Discord message and follows Discord/server message retention practices.
  • Access-control records: the owner-managed approved-server list stores server IDs and who/when approved them; the global no-prefix list stores user IDs and who/when granted access.
  • Operational logs: runtime errors and diagnostic messages are written to hosting logs. If CONSOLE_LOG_CHANNEL_ID is configured, console output is also mirrored to that Discord channel and may contain server/channel names, user tags or IDs, and error context.
  • Optional public lookups: YouTube notification mode retrieves public channel/feed data and checks recent messages in the configured notification channel to avoid reposting videos. Wikipedia commands send the requested search term to Wikipedia's public API.

2. Purposes

The Bot uses this information to execute commands, route and administer support tickets, maintain server settings, perform configured moderation and verification, manage temporary voice rooms, calculate staff activity totals, support AFK/quote utilities, deliver optional notifications, prevent abuse, troubleshoot faults, and maintain service operation.

3. Where information is stored and disclosed

Selected settings and feature records are stored in Firebase/Cloud Firestore. The Bot may run on a hosting provider such as Render, which can hold operational logs. Discord stores messages, role changes, audit-log entries, ticket-log posts, and transcript attachments sent through Discord. These records are subject to Discord's systems and the permissions and retention practices of the relevant server.

Information may be available to server administrators and authorized staff with access to ticket, moderation, activity, or logging channels. Infrastructure providers process information to provide their services. Information may also be disclosed when required by law or reasonably necessary to protect safety, security, or rights. The maintainers do not control Discord's independent processing; see Discord's Privacy Policy.

The maintainers do not sell personal information.

4. Retention and deletion

Retention differs by feature. The reviewed code does not implement one global retention period or automatically delete every stored record when the Bot leaves a server.

  • Pending ModMail: messages and attachment metadata are kept in Firestore until the ticket is created or the code determines that no eligible support server is available. The reviewed code does not set an automatic expiry for abandoned pending-ticket records, so a request left unfinished may remain stored until handled or manually removed.
  • Ticket records and transcripts: closing a ticket changes its Firestore metadata to closed; the record is not deleted in the close flow. The ticket channel is scheduled for deletion about five seconds later. A transcript uploaded to the configured Discord log channel is not automatically deleted by the Bot and may remain there according to that server's retention practices.
  • Warnings and strikes: records remain until a supported moderation command removes them or a maintainer/admin deletes them from the relevant storage. The Bot does not apply a universal time-to-live.
  • Staff activity: scheduled daily reset writes zeroes to existing totals rather than deleting the Firestore records. The Bot has a command to remove a member's activity record, subject to its permissions.
  • AFK and voice records: AFK records are normally removed when the member next speaks in that server. Temporary voice-room records are deleted when the Bot successfully cleans up the associated temporary channel, but stale records can remain if cleanup does not run or fails.
  • In-memory state: snipe cache is capped at 15 messages per channel and clears on process restart; quote state expires after about one hour; captcha state has short timeouts. These are not Firestore retention controls.
  • Configuration and access lists: server configuration and approved-server/no-prefix records are not automatically erased merely because the Bot is removed. The owner/server administrator must clear supported settings or remove the corresponding records.
  • Discord messages and provider logs: the Bot cannot automatically guarantee deletion of transcript attachments, messages already posted to Discord, Discord audit logs, or hosting/provider logs.

5. Your choices and requests

You can stop sending the Bot messages, ask server administrators to disable optional features, or remove the Bot if you have permission. For a review or deletion request, contact the maintainer privately. If you do not already have a private contact route, use the project repository to ask for one, but do not post message contents, private ticket information, or other personal data in a public issue. State the relevant server and feature only to the extent needed to locate the record.

Requests may not be fully achievable where the Bot has no deletion function for the relevant record, where information is retained by Discord or another provider, or where retention is necessary for legal or security reasons. The maintainers should confirm what can actually be found and deleted before promising a timeframe.

6. Security

The Bot relies on Discord permissions, Firebase access controls, and the deployment environment. No online service can guarantee complete security. Server owners should restrict ticket/moderation/activity-log channels to appropriate staff. The Bot owner should protect the Discord token and Firebase service-account credentials, and restrict any optional console-log channel.

7. Children and age

The Bot is intended to be used by people permitted to use Discord under Discord's applicable age requirements and terms. Do not use the Bot to solicit sensitive information from children.

8. Changes

This policy may be updated when the code, deployment, providers, or data practices change. The latest policy will be published at this URL with an updated effective date.

9. Contact

For general questions, visit the F.R.I.D.A.Y GitHub repository. For privacy requests, ask the maintainer for a private contact route and do not include sensitive information in a public issue. The maintainers should publish a dedicated privacy contact method before relying on this policy for a wider public rollout.
